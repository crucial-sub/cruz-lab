- 시각 문서: [visual-plans/2026-11-06-cruz-lab-audit-2-problems-and-plan.html](./visual-plans/2026-11-06-cruz-lab-audit-2-problems-and-plan.html)

## 0. 결론 먼저

1. **이 블로그의 최우선 과제는 "쓰기 마찰"이다.** 코드가 아니라 데이터 구조가 원인이다. 초안이 브라우저 `localStorage`에만 있어서 다른 기기·모바일에서 이어 쓸 수 없고, 비공개 글은 관리자 목록에 나오지 않으며, 출간은 외부 서비스 4곳을 거친다. 2026-05-05 이후 6개월 동안 새 글이 없다는 사실이 이 구조의 결과다.
2. **보안 구멍이 2개 있다.** (a) Firestore·Storage 쓰기 규칙이 `request.auth != null`이라 아무 Google 계정이나 이 프로젝트에 로그인하면 글·시리즈·이미지를 쓰고 지울 수 있다. (b) `/api/posts/by-slug`가 인증 없이 비공개 글 본문을 돌려준다. 두 개 모두 즉시 고쳐야 한다.
3. **저장소 5곳 중 3곳은 역할이 겹치거나 죽어 있다.** Firestore(원본), `data/post-archive`(백업), `content/posts`(2026-05까지의 사본 57개, 코드가 읽지 않음), `localStorage`(초안), Storage(이미지). 원본 1곳 + 자동 백업 1곳으로 줄여야 한다.
4. **편집기는 "소스 모드 CodeMirror"다.** 옵시디언 같은 라이브 프리뷰도, velog 같은 분할 미리보기도 없다. 명령 체계·단축키·플러그인을 등록할 구조 자체가 없다. 수정이 아니라 교체가 맞다.
5. **Astro + React 구조 자체는 맞다.** 문제는 React를 장식(틸트·글로우·마그네틱·글자별 등장)에 19개 아일랜드로 쓰고, 정작 React가 필요한 관리자·에디터가 가장 약하다는 점이다. 공개 페이지에서 React를 빼고, 관리자·에디터에 React를 집중한다.
6. **UI는 2021~2023년 포트폴리오 템플릿 문법이다.** 커스텀 커서, 타이핑 롤 텍스트, 3D 틸트 카드, 글자별 회전 등장, 로고 그리드. 2025~2026년 개발 블로그의 기준(콘텐츠 우선, 큰 타이포, 절제된 모션, 글 상세 중심)과 거리가 있다. 글 상세 페이지에는 목차·이전다음·시리즈·코드 복사가 없다. 사이트의 방향은 "블로그가 본체, 포트폴리오는 `/about` + `/projects` + PDF"로 정한다(10.2).
7. **시리즈는 독립 기능으로는 과투자다.** 시리즈 2개가 태그 2개와 정확히 같은 집합이고, 코드 2,514줄(src의 16%)이 들어갔고, 수정 화면은 깨져 있다. 독립 컬렉션·관리 화면을 없애고 글의 필드(`series: {key, order}`)로 축소한다. 분류의 주축은 제목 접두사를 승격한 `category` + `tags`로 간다(10.1).
8. **관리자 기능에 동작하지 않는 부분이 있다.** 시리즈 수정 API(`exists()` 호출), 시리즈 진행률(쓰는 코드 없음), 비공개 글 관리, 글 삭제 후 이미지 잔존.

개선은 5단계로 간다. 1) 보안·버그 즉시 수리 → 2) 데이터 모델 재설계(초안 서버화) → 3) 에디터 교체 → 4) 공개 사이트 재설계 → 5) 관리자 재구성과 백업 자동화. 상세는 8절.

## 1. CMS 방식 분석

### 1.1 성능

| 항목 | 지금 | 평가 |
|---|---|---|
| 출간 1회 외부 호출 | 모달 열기 5회(토큰 1, GitHub 3, 사이트 fetch 1) + 출간 5~7회(토큰 1, Firestore 2, GitHub 2~4) | 출간 버튼을 누르고 결과를 보기까지 GitHub API 왕복이 직렬로 들어간다. 백업은 출간 경로 밖으로 빼야 한다 |
| 관리자 API 인증 | 호출마다 `identitytoolkit accounts:lookup` REST 1회 | firebase-admin이 이미 서버에 있다. `verifyIdToken`은 공개키 캐시로 네트워크 없이 검증한다 |
| 대시보드 진입 | GitHub 3회 + 공개 사이트 fetch 1회를 매번 | 상태 확인은 요청 시 버튼으로 바꾸면 된다 |
| 공개 글 목록 | Firestore 전체 문서(본문 포함, 266 KB)를 읽고 메모리에서 필터 | 56편에서는 문제없다. 수백 편이면 본문을 뺀 요약 컬렉션이 필요하다 |
| `/blog/` HTML | 353 KB (카드 55개 서버 마크업 + props 48 KB) | 페이지네이션이나 "더 보기"가 없다. 목록은 Astro 정적 마크업으로 충분하다 |
| 함수 리전 | `iad1` ↔ Firestore 리전 미확인 | 서울 사용자 → 미국 함수 → Firestore 왕복. 리전을 맞추면 콜드 요청이 수백 ms 준다 |
| 메모리 캐시 | 인스턴스별 60초 | 출간 직후 "공개 페이지 보기"를 눌렀을 때 다른 인스턴스나 CDN이 옛 글을 줄 수 있다. 출간 시 CDN 퍼지가 없다 |

성능 자체가 지금 가장 큰 문제는 아니다. 이전 세션의 캐시 작업으로 공개 페이지는 빨라졌다. 문제는 **출간 경로에 불필요한 외부 의존이 직렬로 들어간 구조**다.

### 1.2 작성·업로드 플로우의 비효율

1. **초안이 서버에 없다.** 데스크톱에서 쓰다 만 글을 폰에서 이어 쓸 수 없다. 브라우저 데이터를 지우면 사라진다. 대시보드의 "전체 포스트 수"가 기기마다 다르다.
2. **비공개 글이 관리 화면에서 사라진다.** `isPublic: false`로 출간하면 Firestore에는 `status: 'draft'`로 들어가지만 관리자 목록은 published만 보여 준다. 실제로 1건이 이미 고아 상태다. "일단 올려두고 다듬기"가 불가능하다.
3. **출간 전 본문을 렌더해 볼 수 없다.** 에디터는 소스 모드이고 출간 모달에는 카드 미리보기만 있다. 결과를 보려면 출간해야 한다. 비공개 미리보기 URL도 없다.
4. **수정 시 로컬 초안이 서버 원본을 조용히 덮어쓴다.** 어느 쪽이 최신인지 묻지 않는다.
5. **slug를 손으로 쓴다.** 제목에서 자동 제안하는 함수가 있는데 쓰지 않는다.
6. **이미지가 고아가 된다.** 글을 지워도 Storage 이미지는 남는다. 이미지 목록을 볼 화면이 없다. 어떤 글이 어떤 이미지를 쓰는지 기록이 없다.
7. **이미지 처리가 브라우저 Canvas다.** EXIF 회전 정보가 사라진다. PNG는 압축 없이 그대로 올라간다(스크린샷 PNG가 대부분인 기술 블로그에서 용량이 크다). WebP/AVIF 변환, 폭별 변형이 없다.
8. **출간마다 `main`에 커밋이 생긴다.** 백업 커밋이 `main`으로 가면 Vercel Git 연동이 재배포를 돌린다(Ignored Build Step 설정 여부는 미확인). 글 출간과 코드 배포가 섞인다.
9. **읽기 시간 공식이 2개다.** 에디터는 공백 분리 단어 수(한글에 불리), 이관 스크립트는 한글 글자 수 보정.

### 1.3 사용자(필자) 관점에서 불편한 것, 쓸데없이 복잡한 것

- 출간 모달의 "출간 시스템 상태" 6항목(저장소·브랜치·백업 경로·공개 사이트 origin)은 운영자가 아니라 개발자를 위한 정보다. 글을 쓰는 순간에는 소음이다. 하나라도 실패하면 글을 못 올린다(GitHub API 장애 = 출간 불가).
- 에디터 상단의 "Publish Readiness" 5칸 카드가 본문보다 먼저 온다. 글을 쓰기 전에 체크리스트를 본다.
- 하단 버튼 7개(나가기, 내보내기, 불러오기, 초안 폐기, 임시저장, 출간하기, 상태 문구)가 한 줄에 있다.
- 관리자 진입점이 없고 `/admin`을 외워야 한다. 로그인 후에도 사이트 헤더에는 관리자 링크가 없다.
- 관리자 페이지 3종이 서로 다른 방식으로 React를 띄운다. 에디터 페이지는 사이트 레이아웃 밖에 있고 바깥 배경이 항상 흰색이다.

### 1.4 저장소가 적재적소인가

| 저장소 | 지금 역할 | 판단 |
|---|---|---|
| Firestore `posts` | 원본 | 유지. 단, 초안·리비전·요약 구조가 없다 |
| Firestore `series` | 시리즈 | 유지. 글 → 시리즈 방향 연결이 없어 글 상세에서 못 쓴다 |
| Firebase Storage | 이미지 | 유지. 메타데이터(어느 글, 크기, 변형)가 없다 |
| GitHub `data/post-archive` | 출간 시 동기 백업 | 역할은 맞지만 **위치가 틀렸다**. 출간 요청 안에서 동기로 하지 말고, 별도 작업(GitHub Action 또는 서버 cron)이 Firestore를 읽어 `content` 브랜치나 별도 저장소에 쓰는 방식이어야 한다 |
| GitHub `content/posts` | 죽은 사본 57개 | 삭제. Firestore와 내용이 다른 파일이 있고(태그 포맷, 최신성), 빌드 때 파싱만 한다 |
| GitHub `public/uploads` + `upload-asset` API | 쓰지 않는 경로 | 삭제 |
| `functions/` | 빈 Cloud Function | 삭제 |
| `localStorage` 초안 | 유일한 초안 저장소 | 오프라인 임시 버퍼로만 남기고, 원본은 서버 `drafts`로 |
| `sessionStorage` 출간 피드백 | 배너 표시용 | 유지해도 되지만 서버 `publishLog`가 있으면 불필요 |

## 2. 마크다운 편집기 분석

### 2.1 원했던 것과 지금

| 원했던 것 | 지금 |
|---|---|
| 옵시디언 수준의 편집 경험 (기호가 렌더되어 보이는 라이브 프리뷰) | 소스 모드. `#`, `**`, `![]()` 기호가 그대로 보인다 |
| 단축키 자유 등록 | 12개 하드코딩. 등록 UI·설정 없음 |
| `/` 명령으로 커스텀 동작 | 9개 고정 버튼 그리드. 검색·키보드 탐색 없음 |
| 내가 만든 플러그인 등록 | 확장 지점 없음. 모든 동작이 컴포넌트 안 closure |
| 블로그 위에서 바로 쓰고 올리고 고치기 | 쓰기는 되지만 결과를 못 보고, 초안은 기기에 묶이고, 모바일은 고려 안 됨 |

### 2.2 왜 "저열하게" 느껴지는가 (원인)

1. **표시 모델이 소스 모드다.** 옵시디언의 체감은 "쓰는 줄만 기호가 보이고 나머지는 렌더된 문서"에서 온다. 지금은 문서 전체가 기호 투성이다. 글 구조(제목 계층, 인용, 이미지)를 눈으로 못 본다.
2. **단축키가 `Mod+Alt+숫자/문자` 조합이다.** macOS에서 `Option+숫자/문자`는 특수문자 입력 키다. CodeMirror가 base key로 매칭을 시도하지만, 브라우저·한글 IME 상태에 따라 먹지 않는 경우가 생긴다. 옵시디언·노션은 `Mod+Shift+숫자`, `Mod+E`, `Mod+Option` 대신 입력 규칙(`## `+스페이스)을 쓴다.
3. **명령 체계가 없다.** 단축키 12개, 빠른 삽입 9개, 플로팅 버튼 2개가 각각 다른 코드 경로로 같은 함수를 부른다. "명령 → 키 바인딩 → 메뉴 항목"이 하나의 레지스트리에서 나오지 않는다. 그래서 새 동작을 넣을 때 세 군데를 고쳐야 하고, 사용자 설정은 불가능하다.
4. **미리보기가 없다.** 소스 모드라도 분할 미리보기가 있으면 결과를 보며 쓴다. 지금은 그것조차 없다.
5. **에디터가 React 트리의 잎이 아니라 상태의 근원이다.** 키 입력마다 `FullScreenEditor` 전체(메타 패널, 카드 미리보기, 준비도)가 리렌더된다. CodeMirror 자체는 비제어라 입력은 끊기지 않지만, 긴 글에서 `buildDraftData` 재계산과 패널 리렌더가 매 키마다 돈다.
6. **모바일에서 쓸 수 없다.** 터치 키보드 위 툴바가 없고, `Mod` 키 단축키는 모바일에 없다. 992px 폭 레이아웃을 그대로 줄인다.
7. **이전 세대 AI와의 작업 흔적.** `docs/`에 라이브 프리뷰 이전 계획, 엔진 평가 문서가 있고 코드는 다른 방향(소스 모드 CodeMirror)으로 끝났다. 계획과 결과가 갈라진 상태에서 멈췄다.

### 2.3 편집기 엔진 선택

목표: (1) 쓰는 동안 문서가 렌더되어 보인다 (2) 명령·단축키·슬래시 메뉴·플러그인이 하나의 확장 모델에서 나온다 (3) 마크다운으로 저장·내보내기가 정확하다 (4) 모바일에서 쓸 수 있다 (5) 이미지 드롭·붙여넣기, 코드 블록, 표, 콜아웃을 지원한다.

| 후보 | 모델 | (1) 렌더 | (2) 확장 | (3) 마크다운 | (4) 모바일 | 비고 |
|---|---|---|---|---|---|---|
| 지금 CodeMirror 6 소스 모드 | 텍스트 에디터 | 없음 | keymap/확장 가능하나 현재 미구현 | 완벽(원문 그대로) | 약함 | 유지 시 라이브 프리뷰를 직접 만들어야 함(데코레이션으로 기호 숨김·위젯 삽입). 옵시디언이 이 방식. 구현량 가장 큼 |
| **Tiptap (ProseMirror)** | 구조화 문서(WYSIWYG) | 완전 렌더 | Extension 모델이 곧 플러그인. `addKeyboardShortcuts`, `addInputRules`, `addCommands`가 표준. 슬래시 메뉴는 Suggestion 유틸 | `tiptap-markdown` 또는 자체 serializer. GFM 표·코드 블록·이미지 OK. 원문 공백·주석 보존은 불완전 | 좋음 (모바일 툴바 패턴 성숙) | 가장 큰 생태계. Notion형 에디터(Novel 등) 오픈소스 다수 |
| Milkdown (ProseMirror + remark) | 마크다운 우선 WYSIWYG | 완전 렌더 | 플러그인 시스템, 슬래시·툴팁 플러그인 제공 | remark AST 기반이라 마크다운 충실도 높음 | 보통 | 생태계가 Tiptap보다 작음. 커스텀 노드 작성 난도 높음 |
| Lexical | 구조화 문서 | 완전 렌더 | 플러그인 모델 | 마크다운 변환기 있으나 GFM 표 등은 직접 | 좋음 | 한글 IME 이슈 이력. 마크다운 왕복이 약함 |
| CodeMirror 6 + 라이브 프리뷰 자체 구현 | 텍스트 + 데코레이션 | 줄 단위 부분 렌더(옵시디언 방식) | 가능 | 완벽 | 약함 | 표·이미지·코드 블록을 위젯으로 그려야 함. 수 주 단위 작업, 유지보수 부담 큼 |

**결정: Tiptap.** 이유:

- 사용자의 목표는 "마크다운 원문을 보며 쓰기"가 아니라 "여러 사람이 보는 곳에 편하게 쓰고 올리기"다. 저장 포맷이 마크다운이면 충분하고, 편집 화면은 렌더된 문서가 맞다.
- 단축키·슬래시·플러그인이 하나의 Extension 모델이다. "내가 만든 플러그인 등록"이 `extensions: [...]` 배열에 항목을 더하는 일이 된다.
- 입력 규칙(`## ` → 제목, `> ` → 인용, ```` ``` ```` → 코드 블록, `- [ ] ` → 체크)으로 옵시디언·노션의 "타이핑만으로 구조 만들기" 체감을 그대로 얻는다.
- 모바일 터치 편집이 검증돼 있다.

마크다운 충실도 문제는 다음으로 막는다: 저장은 **마크다운을 원본**으로 하되, 에디터 상태(ProseMirror JSON)도 같이 저장해 다음 편집에서 JSON을 먼저 연다. 외부에서 마크다운을 고치면 JSON을 버리고 마크다운에서 다시 만든다. 렌더(공개 페이지)는 마크다운만 본다.

### 2.4 새 편집기가 가져야 할 것 (요구사항)

- 명령 레지스트리: `{ id, title, run, defaultKeys, icon, group }`. 단축키·슬래시 메뉴·툴바·명령 팔레트(`Mod+K` 또는 `Mod+P`)가 모두 이 레지스트리에서 나온다.
- 사용자 키맵: Firestore `settings/editor`에 저장. 키 충돌 검사. 맥/윈도 표기 자동.
- 슬래시 메뉴: 입력 즉시 필터, 방향키·Enter, 최근 사용 순.
- 블록: 제목 1~3, 단락, 목록(순서·비순서·체크), 인용, 콜아웃(`> [!note]` 호환), 코드 블록(언어 선택, 복사), 표(행·열 추가), 이미지(캡션, 대체 텍스트, 폭), 구분선, 임베드(YouTube, CodeSandbox, 링크 카드), 수식(선택).
- 이미지: 여러 장 동시 드롭, 업로드 중 자리표시, 실패 시 재시도, 붙여넣기 HTML에서 이미지 추출.
- 모바일: 키보드 위 고정 툴바(굵게, 제목, 목록, 이미지, 되돌리기), 긴 누르기 메뉴 없음, 자동저장만.
- 보기 모드: 편집 / 마크다운 소스 / 미리보기(공개 페이지와 같은 CSS) 3모드 전환. 소스 모드에서 고친 것은 다시 파싱.
- 문서 보조: 개요(제목 트리) 패널, 단어·글자 수, 읽기 시간(한글 보정 공식 하나로 통일), 찾기·바꾸기.
- 저장: 서버 초안에 2초 디바운스 자동저장 + 오프라인 시 `IndexedDB` 큐 → 온라인 복귀 시 전송. 충돌은 `updatedAt` 비교 후 사용자에게 선택.

1. **쓰기 마찰을 플랫폼보다 낮춘다.** 폰에서 메모 → 데스크톱에서 다듬기 → 발행까지 한 흐름. 서버 초안 + 새 에디터 + 모바일 툴바. 플랫폼은 여기서 "충분히 좋음"에 머문다. 자체 블로그는 "내 습관에 맞춤"이 가능하다. 예: 글 하나를 쓰는 동안 조사 메모를 같은 문서의 사이드 노트로 붙이고 발행 시 제외(사용자의 글쓰기 방식 — 쓰다가 조사하고 다시 쓰기 — 를 구조로 지원).

## 4. Astro + React 병행 구조 분석

### 4.1 구조 자체의 평가

Astro(서버 렌더 + 정적) 위에 React 아일랜드를 올리는 구조는 이 사이트의 성격에 맞다. 공개 페이지는 읽기 중심이고, 관리자·에디터는 상태가 많은 앱이다. 두 성격이 다르므로 한 프레임워크로 통일할 이유가 없다. Next.js로 돌아갈 이유도 없다.

### 4.2 적용 방식의 문제

1. **React를 장식에 쓴다.** 아일랜드 19개가 `client:visible`이고 대부분 framer-motion 래퍼다. 카드(`BlogCard`, `ProjectCard`, `SeriesCard`)는 서버에서 `opacity: 0`으로 렌더되고 JS가 돌아야 보인다. 프로젝트 목록 캡처에서 카드가 비어 있는 것이 이 때문이다. 검색엔진·느린 기기·JS 실패 시 콘텐츠가 없다.
2. **콘텐츠 목록을 React가 통째로 가져갔다.** `/blog/`는 Astro가 55개 카드 마크업을 렌더한 뒤 React가 같은 데이터를 props로 다시 받아 하이드레이션한다. HTML 353 KB.
3. **미사용 파일 15개와 템플릿 잔재가 남아 있다.** 두 벌의 `Header/Footer/BaseHead`.
4. **관리자 마운트 방식이 3가지다.** `client:load` / `client:only` / 수동 `createRoot`.
5. **서버 코드가 두 SDK를 섞는다.** 시리즈는 클라이언트 SDK, 글은 Admin SDK. 클라이언트 SDK는 서버에서 보안 규칙의 제약을 받고 번들도 크다.
6. **면접 어필 관점.** 지금 React 코드의 대부분은 애니메이션 래퍼라 "React 역량"의 증거로 약하다. 진짜 앱인 에디터·관리자가 가장 약하다. 어필 순서가 뒤집혀 있다.

### 4.3 가야 할 분담

| 층 | 담당 |
|---|---|
| 공개 페이지 전부 | Astro. 인터랙션은 CSS와 작은 `<script>`(테마, 목차 스크롤, 코드 복사). React 아일랜드 0~2개(검색 팔레트 정도) |
| 관리자 앱 (`/admin/*`) | React 단일 앱. Astro 페이지 하나가 `client:only`로 마운트하고 내부는 React Router. 서버 세션 쿠키로 페이지 레벨 가드 |
| 에디터 | React(Tiptap). 관리자 앱의 일부 |
| 서버 | Astro API 라우트 + firebase-admin만. 클라이언트 SDK는 브라우저 전용 |
| 공유 | `src/lib/content/` 도메인 타입과 마크다운 파이프라인(서버·에디터 공용) |

이렇게 하면 React는 "앱을 만든 증거"로 남고, 공개 페이지는 JS 없이도 완전하다.

### 5.2 부족한 관리 기능

- 글 상태 모델: 초안(미발행) / 발행 / 비공개(발행했지만 숨김) / 예약 발행. 지금은 `isPublic` 하나.
- 리비전: 발행본의 이전 버전을 보고 되돌리기.
- 비공개 미리보기 링크: 발행 전 실제 페이지로 보기(서명된 토큰 URL).
- 글 안에서 시리즈 지정과 순서 지정(지금은 시리즈 편집기에서만).
- 태그 관리: 이름 바꾸기, 합치기(`크래프톤 정글`/`크래프톤정글`), 글 수.
- 이미지 라이브러리: 업로드 목록, 어느 글이 쓰는지, 미사용 삭제.
- 프로젝트 글 편집: 지금은 저장소 파일을 직접 고쳐야 한다.
- 출간 기록: 언제 무엇을 발행·수정했는지 서버 로그.
- 간단한 통계: 조회수(Vercel Analytics 또는 자체 카운터).
- 모바일 관리: 목록 확인, 초안 이어 쓰기, 발행 토글.

### 5.3 운영 방식 제안

- 관리자 진입: 로그인 상태면 사이트 헤더에 작은 "쓰기" 버튼. 단축키 `Shift+N`(새 글) 같은 전역 키. `/admin`은 유지.
- 하루 운영 단위: "오늘 기록" 버튼 → 노트 1개 즉시 생성 → 쓰고 닫음. 주 1회 노트들을 글로 승격.
- 발행 체크는 모달이 아니라 에디터 오른쪽 패널에 상시 표시. 서버 상태 확인은 "문제가 있을 때만" 배너.
- 백업은 보이지 않게. 매일 또는 발행 후 큐로 GitHub Action이 `content` 브랜치에 마크다운을 동기화.

### 5.4 관리자 화면 실행 점검 (2026-11-06 추가, 1단계 세션)

전수조사(1편)는 관리자 화면을 코드로만 봤다. 로그인이 필요해 실행 화면을 캡처하지 못했다. 1단계가 끝난 뒤 사용자가 localhost에 로그인한 상태에서 ego-browser로 직접 점검했다. 대상은 `/admin`, `/admin/posts`, `/admin/series`, `/admin/series/edit`, `/admin/edit?slug=ai-agent-context`, `/admin/posts/new`다. 화면 폭은 1920px과 390px(모바일)이다. 저장·발행·삭제 버튼은 누르지 않았다.

캡처: [admin-dashboard-2026-11.jpg](./visual-plans/cruz-lab-audit-assets/admin-dashboard-2026-11.jpg), [admin-series-edit-2026-11.jpg](./visual-plans/cruz-lab-audit-assets/admin-series-edit-2026-11.jpg), [admin-editor-mobile-2026-11.jpg](./visual-plans/cruz-lab-audit-assets/admin-editor-mobile-2026-11.jpg). 캡처 아래 가운데의 아이콘 4개짜리 검은 알약은 ego-browser가 띄운 도구 막대다. 사이트 요소가 아니다.

**A13 (새 하자, 데이터 손실 위험).**

- 현상: `/admin/series/edit?id=…`(크래프톤 정글)이 이름·슬러그·설명·커버는 채우고 "포스트 관리 (0)"으로 연다. 실제 글은 22편이다.
- 원인: Firestore `series` 문서의 `postIds`가 글의 문서 ID(`qsBO9vhe4BtXRHRAidiN` 등 22개)다. `SeriesEditor.tsx` 119~123행은 `postIds`를 slug로만 맞춘다. 공개 페이지의 `resolveSeriesPosts`는 문서 ID와 slug를 둘 다 지원하지만, 관리자 편집기는 slug만 지원한다.
- 위험: 이 화면에서 "저장하기"를 누르면 `postIds: []`로 저장된다(253행). 공개 `/series/크래프톤-정글`에서 글 22편이 사라진다. WesBos 시리즈(21편)도 같은 형식(문서 ID)이라 같은 위험이 있다. 두 시리즈 모두 확인했다.
- 왜 지금 드러났나: 1단계가 A4(`exists()`)를 고쳐 이 화면이 열리게 됐다. 그 전에는 TypeError로 열리지 않았다.
- 조치: **시리즈 수정 화면에서 저장하지 않는다.** 코드는 고치지 않는다. 시리즈 관리 화면은 2단계에서 제거한다(10.1). 2단계 마이그레이션은 `postIds`의 두 형식(문서 ID, slug)을 모두 읽어야 한다.

## 8. 개선안 (목표 구조와 단계)

### 8.1 목표 데이터 모델 (Firestore 유지)

Firebase를 바꾸지 않는다. 바꿔야 할 것은 컬렉션 구조와 규칙이다. 관계형 DB로 옮겨도 얻는 것(전문 검색, 조인)보다 이전 비용이 크다. 전문 검색은 발행 글 수가 수백 편 이하면 클라이언트 인덱스(Pagefind 또는 JSON + MiniSearch)로 충분하다.

```
posts/{id}
  slug, title, description, category, tags[], series?: { key, order }, kind: 'post'|'note'|'project'
  status: 'draft'|'published'|'unlisted'|'scheduled'
  publishedAt?, scheduledAt?, updatedAt, createdAt
  cover: { kind: 'generated'|'image', assetId? }
  published: { markdown, html?, readingTime, wordCount, toc[] }   // 공개 페이지가 읽는 스냅샷
  draft:     { markdown, editorJson, updatedAt, device }           // 서버 초안. 발행 전까지만 다름
posts/{id}/revisions/{rev}   // 발행할 때마다 published 스냅샷 복사
seriesMeta/{key}              // (선택) 연재 설명 한 줄. 목록·순서는 posts에서 계산. 관리 화면 없음
assets/{id}                   // storagePath, variants{w480,w960,w1600 webp}, width, height, bytes, usedBy[postId], uploadedAt
settings/editor               // keymap, 슬래시 항목 순서, 기본 보기 모드
publishLog/{id}               // postId, action, at, by
```

- 공개 페이지는 `status == 'published'`인 문서의 `published`만 읽는다. 본문 없는 목록 조회를 위해 `select()`로 필드를 제한한다(Admin SDK 지원).
- 초안은 같은 문서의 `draft`에 산다. "발행"은 `draft → published` 복사 + `revisions` 추가 + CDN 퍼지.
- 프로젝트 글(`kind: 'project'`)도 같은 모델로 옮긴다. 프로젝트의 Part 1·2·3 순서는 같은 `series` 필드로 표현한다. 한 메커니즘을 `/projects`(kind=project)와 `/series`(kind=post)가 각각 보여 준다. `src/content/projects`의 메타만 남기거나 그것도 Firestore로.
- `category`는 단일 값이다. 지금 제목 접두사(`[Pintos]`, `[AI]` …, 57편 중 56편)를 그대로 승격한다. `tags`는 다대다 보조 분류로 남기고 정규화한다(10.1).
- 규칙: 클라이언트 SDK는 **읽기만**, 그것도 `status == 'published'`. 쓰기는 전부 서버 API(Admin SDK)에서 관리자 UID 검사 후. Storage도 클라이언트 쓰기 금지, 서버가 서명 URL 발급 또는 서버 업로드.

### 8.2 목표 시스템 구조

```
브라우저(관리자 React 앱) ──세션 쿠키──▶ Astro API (/api/admin/*) ──Admin SDK──▶ Firestore / Storage
                                                     │
                                                     ├─ 발행 시: CDN 퍼지(Vercel API) + publishLog
                                                     └─ 이미지: sharp로 변형 생성 → Storage

Firestore ──(GitHub Action, 매일 + 발행 후 트리거)──▶ GitHub `content` 브랜치 (markdown + assets 목록)
공개 페이지(Astro SSR + CDN 60s) ◀── Admin SDK 읽기(select, 캐시)
```

- 백업은 출간 요청에서 빠진다. GitHub Action이 Firestore를 읽어 `content` 브랜치에 커밋한다. `main`에 커밋이 생기지 않으므로 재배포가 없다.
- 인증: Firebase Auth 로그인 → `/api/admin/session`이 ID 토큰을 `verifyIdToken`으로 검증하고 관리자 UID면 세션 쿠키 발급(`createSessionCookie`). 관리자 페이지 SSR은 쿠키를 검사해 비관리자에게 404. API는 쿠키 검증.
- 함수 리전을 Firestore 리전과 맞춘다(`vercel.json`의 `regions`).

### 10.1 시리즈 기능은 유용한가

**데이터로 본 현재.**

**판단.** 지금 시리즈는 태그 2개를 한 번 더 저장한 것이다. 두 시리즈 모두 "경험(출처)"으로 묶은 것이고, 경험은 태그·카테고리가 맡는 분류다. 시리즈가 태그와 구별되는 유일한 가치는 **작성자가 정한 읽기 순서**와 **닫힌 집합**(1편부터 N편까지)이다. 이 가치가 필요한 글은 "앞 편을 읽어야 뒤 편이 이해되는 연재"뿐이다. 블로그의 글 56편 중 그런 글은 Pintos 5편(Threads 01·02·Priority → UserProgram 01·02), Proxy-lab 2편, 최소 신장 트리 2편 정도다. 그리고 그마저 제목 접두사와 번호로 순서가 이미 드러난다.

프로젝트 탭과의 겹침은 사실이다. 프로젝트 글의 Part 순서는 시리즈와 같은 개념을 다른 데이터 경로(저장소 파일)에 한 번 더 구현한 것이다. "순서가 있는 묶음"이 두 벌 있다.

결론: **독립 기능으로서의 시리즈는 과투자였다. 개념은 버리지 않되 크기를 1/10로 줄인다.**

**결정.**

1. `series` 컬렉션, 관리 화면(`/admin/series*`, `SeriesEditor`, `SeriesList`), 시리즈 API, `SeriesCard`·`SeriesPreview`·`SeriesWidget`·`MiniSeriesCard`를 제거한다.
2. 글에 선택 필드 `series: { key, order }`를 둔다. 에디터 메타 패널에서 기존 key를 고르거나 새 key를 입력한다. 이것이 시리즈의 전부다. 커버·설명·관리 화면은 없다.
3. `/series/[key]` 페이지는 posts를 `series.key`로 모아 생성한다. 글 상세 상단에 "연재 N/M"과 하단에 이전·다음 편을 표시한다. `/series` 목록은 key별 요약(제목, 편 수, 첫 편 날짜)이다.
4. 프로젝트 글의 Part 순서도 같은 `series` 필드로 표현한다(2단계에서 프로젝트 글을 posts로 옮길 때). `/projects`는 `kind: 'project'`인 글을 프로젝트별로, `/series`는 `kind: 'post'`인 글을 key별로 보여 준다. 메커니즘 하나, 보기 둘. 겹침이 사라진다.
5. 기존 시리즈 2개의 처리: `크래프톤 정글`은 태그로만 남긴다(주제가 제각각이라 읽기 순서가 의미 없음). `wesbos30`은 제목의 01~30 번호가 순서이므로 `series: { key: 'wesbos30', order: N }`으로 환원한다. `/series/크래프톤-정글`은 `/blog?tag=크래프톤+정글`로, `/series/wesbos`는 `/series/wesbos30`으로 리다이렉트한다.

**앞으로 시리즈를 쓰는 규칙.** 뒤 편이 앞 편을 전제할 때만 `series.key`를 적는다. 예: "RAG 파이프라인 만들기 1·2·3", "Pintos Project 1→4". 주제(JavaScript), 경험(정글), 프로젝트(Part)는 각각 카테고리·태그·프로젝트가 맡는다. 일상적인 개발 글은 시리즈를 쓰지 않는다. 쓸 일이 없는 것이 정상이다.

**태그를 극대화하는 쪽이 맞다. 단, 태그 하나로는 부족하고 두 층이 필요하다.** 지금 글은 이미 두 층으로 분류돼 있다. 제목 접두사 `[Pintos]`, `[AI]`, `[자료구조]`(57편 중 56편)가 **카테고리**(단일, 주제 축)이고, `tags`가 보조다. 코드만 이것을 모른다. 그래서:

- `category` 필드를 만들고 접두사를 그대로 옮긴다. 값은 10~12개로 고정한다: AI, JavaScript, React, ReactNative, 운영체제, 자료구조, 알고리즘, 네트워크, 컴퓨터구조, 회고(에세이). `wesbos30`은 카테고리가 아니라 JavaScript 카테고리의 연재다.
- `tags`는 자유 입력을 유지하되 정규화한다: 소문자·공백 규칙, 별칭 합치기(`크래프톤 정글`/`크래프톤정글`), 글당 최대 3개, 관리 화면에서 이름 바꾸기·합치기.
- 목록 UI는 카테고리가 1차 축(왼쪽 또는 상단 탭 10개), 태그는 검색과 글 하단의 보조 링크다. 25개 태그 칩을 기본으로 펼쳐 놓는 지금 방식은 버린다.
- 제목에서 `[접두사]`를 뗀다. 카테고리가 표시를 대신한다. 기존 글의 제목은 마이그레이션 때 일괄 변환한다. 접두사가 곧 카테고리가 아닌 경우도 있다(`[Pintos]` → category 운영체제 + tag pintos + series pintos). 접두사 → 카테고리 매핑 표는 2단계 Plan에 적는다.

### 10.2 포트폴리오 랜딩인가, 블로그인가

**사실.** 지원할 때는 PDF 이력서가 필수이고 PDF 포트폴리오를 받는 회사가 많다. 면접관이 블로그 홈을 보고 오는 징후는 약하다. 읽히는 것은 이력서에 직접 링크한 **프로젝트 글**이다. 이 사실은 사용자의 지원·면접 경험에서 나왔다.

**판단.** 웹 포트폴리오 홈이 하던 일은 "링크를 눌렀을 때 10초 안에 사람을 파악하게 하기"다. 그 일은 히어로·스킬 그리드·경력 아코디언이 아니라 **한 화면짜리 소개**와 **깊이 있는 프로젝트 글**이 더 잘한다. 실제로 읽히는 것도 그쪽이다. 따라서 "블로그 노선"은 포트폴리오를 버리는 것이 아니라 **포트폴리오를 랜딩에서 `/about` + `/projects` + PDF로 옮기는 것**이다.

| 역할 | 지금 | 목표 |
|---|---|---|
| 10초 파악 | 홈 히어로 + 7섹션 (읽을 것이 많음) | `/about` 1화면: 한 줄, 하는 일, 프로젝트 4개 한 줄씩, 이력서 PDF, 연락처 |
| 깊이 확인 | `/projects` Part 글 (유지) | 유지. 이력서에 직접 링크. 측정값·설계 결정을 글 안에 |
| 제출용 | 없음 (웹 링크로 대체) | PDF 포트폴리오. `~/projects/career`에서 관리(이 저장소 밖). 프로젝트 글과 같은 원고에서 생성 |
| 홈 | 포트폴리오 랜딩 | 최신 글·노트 + 2줄 소개 + about 링크 |

**이 방향의 조건.** 글이 없는 블로그는 비어 보인다. 그래서 두 가지를 같이 한다.

1. **노트(`kind: 'note'`)를 공개 스트림으로 둔다.** 짧고 거친 기록을 그날 올린다. 홈과 `/notes`에 보인다. 2주 공백이 있어도 사이트가 살아 있어 보인다. 이것이 "개인 노트로라도 막 쓰는 습관"의 자리다.
2. **최소 운영 규칙을 정한다.** 노트는 배운 날, 글은 2주에 1편. 노트 3~5개가 모이면 글 1편으로 승격한다. 이 규칙을 지키게 하는 것이 2·3단계(서버 초안, 새 에디터, 모바일)의 목적이다.
3. **about은 글이 없어도 완전하다.** 홈이 비어도 `/about`과 `/projects`는 포트폴리오 역할을 한다.

### 10.3 `docs/`를 git으로 관리할 것인가

- 이전 문서 23개는 이 재건으로 교체될 코드를 설명한다. 재건이 끝나면 전부 낡은 문서가 된다. 저장소에 넣으면 "어느 문서가 현재인가"를 또 가려야 한다.
