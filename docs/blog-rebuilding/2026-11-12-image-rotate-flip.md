## 3. 설계

### 3.1 변환

1. 변환은 `{ rotate: 0 | 90 | 180 | 270, flip: boolean }`이다. 뜻은 "좌우반전(flip) 뒤 시계 방향 회전(rotate)"이다.
2. sharp 0.34.4는 한 파이프라인에서 호출 순서와 상관없이 flop을 먼저, rotate를 나중에 적용한다(3×2 픽셀 시험). 그래서 위 정의를 그대로 `flop()` · `rotate(r)`로 만든다.
3. `rotate`를 `resize`보다 먼저 부르면 `resize`는 돌린 뒤의 폭을 기준으로 한다(1000×600을 90° 돌려 폭 480 → 480×800).
4. 단추 하나를 더하는 규칙(보이는 그림 기준):
   - 오른쪽 90°: `(f, r+90)`
   - 왼쪽 90°: `(f, r-90)`
   - 좌우반전: `(!f, -r)`. 돌린 그림을 뒤집으면 회전 방향이 반대가 된다(F∘R(r) = R(-r)∘F).
5. 규칙 코드: `src/lib/asset-transform.ts`(순수 함수).

### 3.2 서버: 파생 자산

1. API: `POST /api/admin/assets/{id}/transform`, 본문 `{ op: 'rotate-left' | 'rotate-right' | 'flip-horizontal' }`, 응답 `{ asset }`(finalize와 같은 모양).
2. 파생 자산은 언제나 원본(root)에서 만든다. 파생 자산 B를 돌리면 원본 A와 합친 변환으로 만든다. 그래서 여러 번 눌러도 다시 압축은 한 번이다.
3. 합친 변환이 처음 방향이면 원본 A를 준다(새 파일 없음).
4. 같은 원본 · 같은 변환의 ready 자산이 있으면 그것을 준다(`where('derivedFrom', '==', root)`).
5. 없으면 원본의 최대 변형(webp)을 받아 돌리고 업로드와 같은 규칙(`planVariants`)으로 변형을 만든다. 업로드 원본은 finalize 때 지웠기 때문이다(EXIF · GPS 제거, 2단계 D6).
6. 새 자산 문서는 업로드 자산과 같은 모양에 칸 2개를 더한다: `derivedFrom`(원본 ID), `transform`. 아직 어느 글도 쓰지 않으므로 `orphanedAt`을 적는다(finalize와 같다).
7. 원본 문서가 없으면(정리됨) 지금 자산을 원본으로 삼는다.
8. 거절(422 `NOT_TRANSFORMABLE`): 옛 이미지, 영상, 업로드가 끝나지 않은 자산. 움직이는 이미지는 422 `ANIMATED_NOT_SUPPORTED`다. sharp가 돌리지 못한다("Rotate is not supported for multi-page images").
9. 파일을 올린 뒤 문서 쓰기가 실패하면 그 자산의 파일을 지운다. 문서 없는 파일은 정리가 찾지 못한다.

### 3.3 정리(purge) 보호

1. 정리 직전 재검사에서, 쓰이는 파생 자산의 원본도 "쓰임"으로 본다(`withDerivedRoots`).
2. 이유: 원본이 있어야 다시 돌리거나 원래 방향으로 돌아올 수 있다. 원본은 글이 쓰지 않으므로 고아가 된다. 보호가 없으면 7일 뒤 지워진다.
3. 쓰이지 않는 파생 자산은 기존 규칙대로 고아가 된 지 7일 뒤 정리된다.

### 3.4 에디터 메뉴

1. 이미지 메뉴의 정렬 줄 아래에 "돌리기" 줄을 둔다: `↺ 왼쪽 90°`, `↻ 오른쪽 90°`, `⇆ 좌우반전`. 기호는 화면 낭독기가 읽지 않는다(`aria-hidden`).
2. 누르면 입력 중인 칸을 먼저 반영한다(단추가 포커스를 옮기지 않는다, 병합 준비 문서 6.5). 기다리는 동안 세 단추를 끄고 누른 단추에 "돌리는 중…"을 보인다.
3. 응답을 받으면 새 그림을 미리 받는다(최대 5초). 그다음 노드의 `src`가 그대로일 때만 `src`를 바꾼다(`replaceImageSrcKeepingSelection`). 한 트랜잭션이라 되돌리기 한 번이면 옛 `src`로 돌아간다. 이미지 노드 선택을 지켜 메뉴가 닫히지 않는다.
4. 폭 · 정렬 · 대체 · 캡션은 그대로다. 폭(px)을 정했으면 같은 폭에서 돌린 비율로 그린다.
5. 실패하면 메뉴에 글자로 알린다(`role="alert"`). 메뉴가 닫히거나 이미지가 바뀌면 지운다.
6. 단추를 켤 이미지는 주소로 정한다(`imageTransformTargetOf`): 이 블로그 버킷의 `assets/{id}/…`. 우리 버킷의 다른 경로는 "옛 이미지는 돌릴 수 없습니다", 그 밖은 "이 블로그에 올린 이미지만 돌릴 수 있습니다", 영상은 "영상은 돌릴 수 없습니다".
7. 메뉴 단추는 기존 메뉴의 mousedown 막기를 그대로 따른다. 그래서 iPhone에서도 한 번 탭으로 눌린다(병합 준비 문서 6.5).

### 3.5 공개 렌더 · OG · RSS

1. 공개 렌더는 바꾸지 않았다. 파생 자산도 `variants`가 있으므로 `rehype-assets`가 srcset · width · height를 붙인다. 높이는 돌린 비율이다.
2. OG 카드는 글자 카드다(본문 이미지 없음). RSS는 제목 · 설명만 담는다. 그래서 본문 이미지 주소가 바뀌는 것으로 모든 화면이 같은 모양이 된다.

### 3.6 속도 줄이기 (사용자 요청 2026-11-12)

사용자가 iPhone 확인에서 새 모양을 만드는 데 약 5초가 걸린다고 했다(5.7). 단계별 시간(Server-Timing)을 재 보니 대부분이 변형 파일 올리기였다(5.8).

1. 변형 파일 4개를 동시에 올린다. 하나가 실패하면 모두 끝난 뒤에 실패로 본다. 그래야 실패 뒤 정리가 늦게 끝난 파일을 놓치지 않는다.
2. 다운로드 주소를 직접 만든다(`firebaseDownloadUrl`, `src/lib/asset-url.ts`). `getDownloadURL`은 파일마다 메타데이터를 한 번 더 받아 토큰을 읽는다. 토큰은 서버가 정하므로 그 요청이 필요 없다. 모양은 firebase-admin 소스(`lib/storage/index.js`의 `getDownloadURL`)와 같다. 업로드 완료(finalize)도 같은 함수를 쓰므로 함께 빨라진다.
3. 원천을 한 번만 풀고 돌린 픽셀에서 크기 4가지를 동시에 만든다. 전에는 크기마다 webp를 다시 풀었다.
4. 원본 문서 읽기와 같은 원본의 파생 자산 찾기를 동시에 한다.
5. 에디터는 단추를 누르는 즉시 그림을 CSS로 돌려 보인다(`transformPreviewCss`). 90°는 돌린 그림이 지금 자리 안에 들어오게 줄인다(가로 1000 · 세로 600이면 0.6배). 서버가 주소를 주면 같은 렌더에서 `src`를 바꾸고 미리 보기를 지운다. 이 CSS는 저장하지 않는다.
6. 회전 API 응답에 Server-Timing(`read` · `dl` · `img` · `up` · `write` · `total`)을 붙인다. 관리자 API라 공개 응답에는 없다.

## 6. Claude 판단

사용자 결정과 다르게 한 것은 없다. 아래는 결정이 다루지 않은 부분의 판단이다.

1. 움직이는 이미지(GIF · 움직이는 webp)는 돌리지 않는다. sharp가 여러 프레임 회전을 지원하지 않는다. 좌우반전은 되지만 단추마다 결과가 다르면 헷갈리므로 셋 다 거절한다.
2. 원본 문서가 없으면 지금 자산을 원본으로 삼는다. 정리 보호(3.3)가 있어 보통은 생기지 않는다.
3. 작은 변형 주소(옛 크기 버튼으로 넣은 초안)도 돌린다. 결과는 새 자산의 최대 변형 주소다. 그래서 그 초안의 이미지는 공개 페이지에서 srcset을 얻는다.
4. 폭(px) 속성은 돌려도 그대로 둔다. 같은 폭에서 돌린 비율로 그린다.
5. 새 그림을 미리 받은 뒤 `src`를 바꾼다. 빈 칸이 깜빡이지 않게 한다.
6. 공개 렌더 확인은 발행 대신 같은 렌더러로 한다(5.3).
7. 스모크 스크립트를 저장소에 둔다(`scripts/smoke/`, 다른 스모크와 같은 자리). 개발 서버 기준 주소의 기본값은 4335다.
8. 다운로드 주소를 직접 만드는 것은 에뮬레이터(`STORAGE_EMULATOR_HOST`)를 다루지 않는다. 이 저장소는 에뮬레이터를 쓰지 않는다.
9. 미리 돌려 보이기는 150ms 전환 동안 그림 모서리가 잠깐 자리 밖으로 나간다(돌면서 줄어드는 중). 끝난 상태는 자리 안이다. 그림을 받기 전에 누르면(크기 0) 줄이지 않는다.
10. 영상 업로드 완료(finalize)의 주소는 바꾸지 않았다(`getDownloadURL` 그대로). 새로 올리는 파일이 없고 메타데이터만 바꾸기 때문이다.
